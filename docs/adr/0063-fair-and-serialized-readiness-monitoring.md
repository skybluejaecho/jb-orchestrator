# ADR 0063: Worker 배정 Monitor는 공정하게 순회하고 프로젝트별 평가를 직렬화한다

## 배경

ORCH-064의 Monitor는 한 cycle의 프로젝트 수를 제한하지만 항상 같은 정렬의 첫 페이지를
조회했다. active 프로젝트가 제한보다 많으면 뒤쪽 프로젝트가 계속 평가되지 않을 수 있다.
또한 Monitor 프로세스를 둘 이상 실행하면 동일한 READY 발생을 동시에 읽고 같은 경보를
생성하려 할 수 있다. 데이터베이스의 unique 제약은 중복 저장을 막지만 한 Monitor의 cycle을
실패시킬 수 있으며, 한 프로젝트의 오류가 이후 프로젝트 평가까지 막았다.

## 결정

- active 프로젝트는 `created_at DESC, id ASC` 순서의 keyset cursor로 조회한다.
- runtime은 다음 페이지 cursor를 유지하고 마지막 페이지를 처리하면 첫 페이지로 돌아간다.
- 새 프로세스는 첫 페이지부터 시작한다. 평가는 멱등이므로 재시작 시 이미 본 프로젝트를 다시
  평가하는 것을 허용한다.
- 한 cycle은 설정된 project limit까지만 평가하며 다음 페이지 존재 여부를 확인하기 위한 레코드
  하나만 추가 조회한다.
- PostgreSQL에서는 프로젝트 ID로 만든 안정적인 64-bit key에
  `pg_try_advisory_xact_lock`을 적용한다.
- 프로젝트 존재 확인, 진단 읽기, 경보 및 이벤트 갱신은 같은 transaction 안에서 수행한다.
- 다른 Monitor가 lock을 소유하면 현재 진단만 반환하고 경보 원장은 변경하지 않는다.
- 프로젝트별 예외는 해당 프로젝트의 실패로 격리하고 다음 프로젝트 평가를 계속한다.
- runtime은 cycle의 시도·성공·실패 수와 다음 페이지 존재 여부를 구조화 로그로 남기며 마지막
  batch 결과를 프로세스 안에서 관찰할 수 있게 유지한다.

## 결과

장시간 실행되는 Monitor는 제한보다 많은 active 프로젝트를 빠뜨리지 않고 반복 순회한다.
여러 Monitor가 고가용성을 위해 함께 실행되어도 한 프로젝트의 경보 전환은 한 transaction에서만
수행된다. 일시적인 프로젝트 오류가 전체 cycle을 중단하지 않는다. Cursor는 운영 원장이 아니므로
PostgreSQL에 영속화하지 않으며, 프로세스 재시작 후 첫 페이지부터 다시 평가해도 경보 식별과
이벤트 멱등성이 유지된다.
