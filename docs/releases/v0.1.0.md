# v0.1.0 릴리스 후보

## 지원 범위

첫 릴리스는 신뢰할 수 있는 단일 서버의 PostgreSQL·Control Plane과 필요한 Worker, 별도 사용자 PC의
loopback Jarvis, VPN·SSH 터널 또는 별도 관리되는 HTTPS를 통한 클라이언트 연결을 지원한다.
OpenClaw Gateway, GitHub publisher, Webhook notifier는 해당 역할의 설치·자격 증명이 준비된 경우에만
활성화한다. 공개 인터넷 Jarvis, 사용자 로그인/OIDC, Flutter 앱, credential 자동 교체는 범위 밖이다.

## 포함된 기능

- PostgreSQL 원장을 사용하는 버전 고정 Workflow, Phase Pack, Skill, 모델·예산 구성
- 분기·병렬·출력 계약·명시적 승인과 lease 기반 Worker 실행
- API·CLI·MCP ingress와 프로젝트 범위 service-account 인증
- OpenClaw의 사전 구성된 project agent workspace 실행, session 연속성, 관찰·취소
- GitHub review 게시와 Webhook 알림의 내구성 원장·재시도
- 로컬 Jarvis의 요청·실행·운영 상태 관찰 및 명시적 제어
- Worker와 credential readiness, credential rotation·감사 원장
- Runtime/Jarvis 분리 컨테이너와 단일 host 서버·로컬 client Compose

## OpenClaw v0.1 제약

OpenClaw Gateway `v2026.8.1`의 외부 client는 요청별 `cwd`를 지정할 수 없다. 따라서 v0.1은
OpenClaw agent 자체에 repository workspace를 미리 구성하고 Workflow 노드가 `agent_id`로 이를
선택하는 방식만 지원한다. `cwd`, `workspace_mode: git_worktree`, 다른 custom workspace mode가
포함된 Workflow는 옵션 조회에서 비호환 사유가 표시되고 dispatch 전에 차단된다.

동일 checkout을 수정하는 OpenClaw 노드를 병렬 실행하지 않는다. 실행별 격리 worktree는
OpenClaw의 plugin-owned subagent runtime을 사용하는 후속 버전 후보이며 v0.1 범위가 아니다.
과거 pre-release build가 만든 managed-worktree 원장의 inspect/cleanup 경로만 호환 목적으로
유지한다.

## OCI OpenClaw acceptance (2026-09-20)

OCI ARM64 staging host에서 OpenClaw Gateway `v2026.8.1`과 Runtime 후보 이미지를 사용해 다음
경계를 검증했다.

- PostgreSQL migration head `0032_service_account_credentials`, API readiness와 새 Task Worker
  기동이 성공했다.
- persisted device token만 사용한 `jb-openclaw doctor`가 성공했고 Gateway가 `main`과
  `climbing-game` agent를 모두 인식했다.
- `/workspaces/repositories/climbing-game`을 workspace로 설정한 전용 agent에서 idempotent
  replay와 동일 session continuation이 모두 `ok`로 종료됐다.
- `oci-openclaw-readiness@2`의 실제 dispatch가 `climbing-game` agent에서 성공했고 Workflow,
  Run, 외부 실행과 Artifact가 모두 terminal 상태로 수렴했다. 외부 실행의
  `workspace_path`는 `null`이었으며 agent가 보고한 branch와 별도 Git 확인 모두 clean `main`이었다.
- 동적 `cwd`가 남은 v1 dispatch는 HTTP `409`와
  `openclaw.dynamic_cwd_unsupported`로 거절됐고 요청, Workflow, 외부 실행 개수가 변하지 않았다.
- 존재하지 않는 agent에 대한 시작 거절은 provider run ID 없이 외부 실행을 `failed`로 닫고
  `completed_at`과 안전한 실패 분류를 기록했다. `starting` 원장은 남지 않았다.

이 acceptance는 사전 구성 agent workspace 방식의 v0.1 실행 계약을 입증한다. 동적 worktree,
GitHub 게시와 Webhook 전달은 각각 별도의 지원 범위와 acceptance 판정을 따른다.

## main 배포 acceptance (2026-09-20)

`release/0.1.0`을 PR #90으로 `main`에 병합한 뒤 merge commit `45b9d06`에서 최종 후보를
다시 빌드하고 다음 경계를 검증했다.

- `main` push CI의 Quality, Test, System smoke, Jarvis, OpenClaw contract, Deployment contract,
  Runtime·Jarvis container build와 Release readiness 등 9개 check가 모두 성공했다.
- OCI ARM64 host에서 `jb-orchestrator-runtime:main-45b9d06`을 빌드하고 migration head를
  재확인한 뒤 API, Task Worker와 Readiness Monitor를 순차 교체했다. 세 서비스가 동일한 후보
  image ID를 사용했고 API readiness와 OpenClaw device-token doctor가 성공했다.
- 후보 이미지에서 `oci-openclaw-readiness@2`를 실제 dispatch해 Workflow, Run, 외부 실행과
  Artifact가 모두 성공 상태로 수렴했다. `climbing-game` agent는 `gpt-5.6-sol`을 사용해
  repository가 clean `main`이라고 보고했고 별도 Git 확인 결과와 일치했다.
- 운영 PostgreSQL의 custom-format dump를 생성해 권한을 `0600`으로 제한하고 format을 검사했다.
  이를 네트워크와 volume을 공유하지 않는 PostgreSQL 17 tmpfs 인스턴스에 복원했으며 Alembic
  revision `0032_service_account_credentials`와 핵심 원장 row count가 운영 DB와 일치했다.
- 직전 Runtime을 `jb-orchestrator-runtime:pre-main-45b9d06`으로 보존했다. 이 이미지로 현재 DB에
  연결하는 격리 API를 `127.0.0.1:18001`에 기동해 readiness HTTP `200`을 확인한 뒤 제거했고,
  운영 후보 API는 계속 healthy였다.
- `jb-orchestrator-jarvis:main-45b9d06` ARM64 이미지를 비-root로 검증하고 임시 client Compose로
  기동했다. 문서화된 별도 `all_projects` Jarvis service account를 사용해 프로젝트·개요·Workflow
  option·Worker readiness와 UI가 모두 HTTP `200`을 반환했다. 임시 container와 token 파일은
  검증 직후 제거하고 잘못 발급한 project-scoped account는 revoke했다.

운영 Compose의 Runtime image는 `jb-orchestrator-runtime:main-45b9d06`으로 고정했다. GitHub와
Webhook profile은 이 설치에서 활성화하지 않았으므로 실제 외부 게시·알림 acceptance 대상에서
제외하며, 활성화 전 각 provider 자격 증명과 시험 목적지를 별도로 검증한다.

## 릴리스 게이트

| 순서 | 명령·검증 | 완료 기준 | 현재 상태 |
| --- | --- | --- | --- |
| 1 | `uv run --frozen python tools/release/verify_version.py v0.1.0` | Runtime·Jarvis·bundled adapter가 0.1.0 | 통과 |
| 2 | `uv run --frozen jb system release-check` | 자동 품질 10개 gate ready | 통과 |
| 3 | `JB_ENVIRONMENT=test`와 일회용 PostgreSQL에서 `uv run jb system release-check --include-system-smoke` | 실제 process smoke ready | 통과 (PostgreSQL 17 tmpfs) |
| 4 | Runtime·Jarvis 이미지 빌드와 서버·클라이언트 Compose 리허설 | 비 root 실행, 이미지·설정 일치 | 통과 (OCI ARM64 Runtime·Jarvis와 client Compose) |
| 5 | 별도 host/DB에서 백업·복원 및 이전 이미지 rollback 리허설 | 데이터 유지·복구 확인 | 통과 (격리 PostgreSQL 복원·원장 count 일치·이전 API readiness) |
| 6 | 실제 Gateway·GitHub·Webhook acceptance | 필요한 provider 연결·권한 확인 | 통과 (활성 OpenClaw E2E, GitHub·Webhook profile 비활성) |
| 7 | `release/0.1.0` → `main` PR과 버전 tag | CI 통과와 main 포함 commit | main PR #90·CI 통과, `v0.1.0` tag 대기 |

1~6번 gate는 완료됐다. 7번은 검증 증거를 포함한 최종 `main` commit에 annotated tag를 만드는
작업만 남았다. 실제 provider 자격 증명이 없는 설치는 해당 profile을 비활성화하며, 활성화하지
않은 기능은 운영 acceptance 대상에서 제외했음을 기록한다. 제3자 서비스에서 PR 게시나 알림
전송을 검증할 때는 명시적인 시험 저장소·목적지만 사용한다.

## 발행 후

`main`의 병합 commit에 `v0.1.0` annotated tag를 만들고 GHCR workflow 결과를 확인한다. 서버와
로컬 Jarvis는 각각 정확한 `:0.1.0` 이미지 tag로 갱신한다. Release 변경을 `develop`에도 병합한
뒤 다음 개발 버전을 정한다. 설치·복구 명령은 [컨테이너 이미지 릴리스](../operations/container-image-release.md)와
[PostgreSQL 백업·복원](../operations/postgres-backup-restore.md)을 따른다.
